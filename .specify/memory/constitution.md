# 메인블로그 플랫폼 Constitution

티스토리형 블로그 플랫폼(메인블로그 + 개별 블로그)을 만들 때 모든 스펙·계획·구현이 지켜야 하는 원칙입니다.
근거는 [요구사항분석서 1](../../docs/01-requirements/요구사항분석서_1_기본요구사항.pdf)과
[요구사항분석서 2](../../docs/01-requirements/요구사항분석서_2_세부정책_결정기록.pdf)입니다.

## Core Principles

### I. 보안이 먼저다 (NON-NEGOTIABLE)

보안은 기능이 아니라 모든 기능에 걸리는 규칙이다.

- 비밀번호는 bcrypt 해시로만 저장한다. 인증번호·토큰·블랙리스트 개인정보도 원문 대신 해시로 저장한다.
- 로그인은 JWT를 HttpOnly·Secure 쿠키에 담는다. localStorage에 토큰을 두지 않는다. Refresh Token은 DB에 저장해 로그아웃·비밀번호 변경 때 폐기할 수 있어야 한다.
- 인증·인가, CSRF 토큰, 보안 헤더는 Spring Security로 처리한다. 직접 구현하지 않는다.
- 사용자 입력은 서버에서 검증하고, 글 본문은 서버에서 jsoup으로 걸러 보낸다. 화면은 글 본문 외의 입력을 textContent로만 넣는다.
- 가입·비밀번호 찾기 화면은 가입 여부를 드러내지 않는다(같은 문구).

**Why**: 팀 방향이 "보안 중심"이고, 하나만 빠뜨려도 구멍이 생기기 때문이다 (D-09, D-53, D-64).

### II. 역할은 블로그마다 다르다 (NON-NEGOTIABLE)

블로그장·부블로그장·멤버는 계정 종류가 아니라 블로그별 역할이다.

- 모든 요청에서 서버가 그 블로그에서의 역할을 DB로 확인한다. 토큰 안의 정보만 믿지 않는다(토큰에는 회원 번호 정도만).
- A 블로그의 블로그장은 B 블로그를 관리할 수 없다(SEC-07).
- 블로그별 역할 확인은 `@PreAuthorize` 메서드 보안으로 선언해 어느 기능에 어떤 권한이 필요한지 드러낸다.
- 정지·강퇴도 블로그 단위다. 한 블로그의 제재가 다른 블로그 활동을 막지 않는다.

**Why**: 이 플랫폼에서 가장 중요한 보안 항목이다. 한 회원이 블로그마다 다른 권한을 갖기 때문이다.

### III. 개인정보는 필요한 만큼만, 서버에서 가린다

- 이메일·이름·전화번호·닉네임만 받고, 쓰는 곳이 정해진 정보만 받는다(4.6).
- 가리는 처리(마스킹)는 화면이 아니라 서버가 응답을 만들 때 한다. 비밀번호 칸은 어느 화면에도 없다.
- 메인 관리자가 원문을 볼 때는 기록을 남긴다(ADM-06).
- 삭제·탈퇴·폐쇄 데이터는 30일 보관 후 지운다. 예외(인증번호 즉시 삭제, 블랙리스트 해시 보관, 운영 기록 1년)는 스펙에 적힌 것만 허용한다.

### IV. 서버를 늘려도 코드를 고치지 않는다

1차는 서버 1대지만 이중화에 대비해 아래를 처음부터 지킨다(4.3).

- 서버 메모리에 상태를 두지 않는다. 인증 코드, Refresh Token, 로그인 실패 횟수, 조회 기록은 DB에 둔다. IP별 요청 제한만 1차에 메모리에서 세고 이중화 때 Redis로 옮긴다(SCL-01).
- 파일 저장은 `FileStorage` 인터페이스 뒤에 둔다. 1차는 디스크, 이중화 때 S3(SCL-02).
- `@Scheduled` 작업에는 처음부터 ShedLock을 건다(SCL-03). 시간대는 `Asia/Seoul`을 명시한다.

### V. 단순한 것을 고른다

- 같은 문제를 푸는 방법이 여럿이면 추가 서버·비용·설정이 없는 쪽을 고른다(폴링 알림, 볼 때마다 모으는 피드, DB 조회 기록, 서버 디스크 이미지, Gmail SMTP).
- 바꿀 근거(성능 목표 초과, 사용자 증가)가 생기면 그때 다시 검토하고 결정 기록에 남긴다.

### VI. 결정은 기록으로 남긴다

- 정책을 정하거나 바꾸면 [research.md](../../specs/001-main-blog/research.md)의 결정 기록(D-번호)에 이유와 이전 내용을 함께 남긴다.
- 스펙(spec.md)·DB 설계(erd_tables.sql)·결정 기록이 서로 어긋나면 구현 전에 먼저 맞춘다.

## 기술 제약

| 영역 | 정한 것 |
| --- | --- |
| 서버 | Spring Boot, Spring Security |
| DB | MySQL 8 (InnoDB, utf8mb4). 기준 스키마는 `docs/02-database/schema/erd_tables.sql` |
| 화면 | 정적 HTML + JS. 글 상세만 서버가 og 태그를 채움 |
| 성능 | 메인·목록·검색 1초 목표, 늦어도 2초. 5초 넘으면 중단하고 다시 시도 안내 |
| 사용성 | PC·모바일 반응형. 개별 블로그에서도 메인 상단 메뉴와 로그인 상태가 같게 보임 |
| 범위 | 메인블로그만. 개별 블로그 내부 기능(꾸미기, 블로그별 카테고리 세부, 멤버 등급 세부)은 다음 스펙 |

## 문서 작업 방식

- 새 기능은 `/speckit-specify`로 `specs/NNN-이름/`에 스펙을 만들고, `/speckit-clarify` → `/speckit-plan` → `/speckit-tasks` 순서로 진행한다.
- 원본 요구사항분석서(PDF)와 DB 설계 파일은 `docs/` 아래에 그대로 두고, 스펙 문서는 그것을 근거로 링크한다.
- 테이블이나 컬럼을 바꾸면 `erd_tables.sql`, `erdcloud_import.sql`, `erdcloud_names.md`, `data-model.md`를 같이 고친다.

## Governance

- 이 문서는 다른 모든 작업 방식보다 우선한다. 스펙·계획 리뷰 때 이 원칙을 지켰는지 확인한다(plan.md의 Constitution Check).
- 원칙을 바꾸려면 이유를 결정 기록에 남기고 팀이 합의한 뒤 버전을 올린다. 원칙 삭제·뒤집기는 MAJOR, 원칙 추가는 MINOR, 문구 정리는 PATCH.
