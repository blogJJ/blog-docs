### 1. 이메일 인증: Spring에서 6자리 코드 직접 발송·검증

- **Decision**: 외부 인증 서비스 없이 서버가 코드를 만들고 `spring-boot-starter-mail`(JavaMailSender) + Gmail SMTP로 보낸다.
- **Rationale**: 가입 화면을 벗어나지 않고 ① 이메일 인증 → ② 비밀번호 → ③ 이름·닉네임·전화번호가 한 흐름으로 이어진다. 비용·키 관리가 없고 만료·재발송·입력 횟수 규칙을 직접 정할 수 있다.
- **Alternatives considered**: 인증 링크(메일 앱 안 브라우저에서 열리면 흐름이 끊기고, 링크 페이지·토큰 처리를 따로 만들어야 함), Firebase Auth 등 외부 서비스(회원 정보가 두 곳에 나뉘고 규칙을 서비스에 맞춰야 함).
- **구현 절차**:
  1. SecureRandom으로 6자리 숫자를 만든다.
  2. 가입 전이라 회원 번호가 없으므로 이메일 기준으로 DB에 해시해 저장한다. 만료 10분.
  3. 5번 틀리면 무효.
  4. 재발송은 1분에 한 번, 다시 보내면 이전 코드는 무효.
  5. 가입 마지막 단계에서 서버가 인증 완료 여부를 다시 확인한다(화면에서 단계를 건너뛰는 것을 막음).

### 2. 블로그 폐쇄: 누른 날짜 + 7일 04:00, `@Scheduled` 매일 04:00

- **Decision**: 폐쇄 버튼(BLG-09)이나 관리자의 블로그장 강퇴(ADM-07, 부블로그장 없음) 순간 `close_scheduled_at`(그 날짜 + 7일 04:00)을 저장한다. `@Scheduled(cron = "0 0 4 * * *", zone = "Asia/Seoul")`가 매일 예정 시각이 지난 블로그를 모두 폐쇄하고, 같은 배치에서 "폐쇄까지 3일 또는 1일 남은 블로그"를 찾아 알림을 보낸다. 알림 종류는 `BLOG_CLOSING`, 중복 발송은 `blog_close_notices`로 막는다. 서버가 여러 대면 ShedLock으로 한 번만 실행된다.
- **Rationale**: 새벽 4시는 이용자가 가장 적다. "며칠 몇 시에 닫힌다"고 정확히 안내할 수 있고 3일 전·1일 전 알림으로 자기 글을 챙길 시간을 준다. 서버가 꺼져 있던 날이 있어도 다음 날 밀린 것까지 처리된다. 어노테이션 하나로 구현된다.
- **Alternatives considered**: 정확히 168시간 뒤(폐쇄 시각이 흩어져 활동 시간에도 닫히고 배치를 자주 돌려야 함), 조회할 때마다 확인(닫힌 블로그 데이터가 정리되지 않음), Spring Batch(하루 한 번 목록을 닫는 일에 설정이 과함).
- **주의**: `zone`을 꼭 지정한다. AWS 서버 기본 시간대는 UTC라서 빠뜨리면 한국 시간 오후 1시에 실행된다.

### 3. 로그인: JWT + HttpOnly 쿠키 (D-53, 처음 정한 세션 + 쿠키(D-11)에서 변경)

- **Decision**: JWT를 JS가 읽을 수 없는 HttpOnly 쿠키에 담는다. Refresh Token은 MySQL에 저장한다(D-82).
- **Rationale**: 서버를 여러 대로 늘려도 로그인 정보가 토큰 안에 있어 서버끼리 공유할 필요가 없다. HttpOnly라 XSS로 토큰을 훔치기 어렵다. 만료된 Refresh Token은 매일 04:00 배치가 지운다(D-83).
- **Alternatives considered**: 세션 + 쿠키(서버를 늘리면 Spring Session + Redis가 필요). Refresh Token을 Redis에 저장(1차에도 Redis를 따로 띄워야 함), 저장하지 않음(로그아웃·비밀번호 변경 뒤에도 훔친 토큰을 쓸 수 있어 USR-04를 못 지킴).
- **구현할 때 지킬 것**: 로그아웃·비밀번호 변경을 바로 반영하려면 Refresh Token을 DB에 저장하고 폐기할 수 있어야 한다. 쿠키로 보내므로 CSRF 토큰은 계속 필요하다(SEC-10). 정지·강퇴·블로그별 역할은 토큰 내용만 믿지 말고 요청마다 DB에서 확인한다(SEC-07). 토큰에는 회원 번호 정도만 담는다.

### 4. 보안: Spring Security (D-09)

- **Decision**: 보안 헤더, CSRF 토큰, 인증·인가를 Spring Security로 처리한다.
- **Rationale**: CSRF 토큰, 보안 헤더, 세션 고정 공격 방어가 기본으로 들어 있다. 블로그별 역할 확인을 `@PreAuthorize`로 메서드 위에 선언해 어느 기능에 어떤 권한이 필요한지 한눈에 보인다. 실무 표준이라 자료가 많다.
- **Alternatives considered**: 직접 구현(권한 확인을 기능마다 넣으면 하나만 빠뜨려도 구멍이 생기고, 검증되지 않은 코드가 됨).

### 5. 화면: 정적 HTML + JS (D-66, 잠시 정했던 전부 Thymeleaf(D-63)에서 변경)

- **Decision**: 화면은 HTML을 내려주고 JS가 API로 데이터를 받아 채운다.
- **지킬 것**:
  - XSS: 글 본문은 서버가 마크다운을 HTML로 바꾼 뒤 jsoup으로 걸러 API로 보내고(SEC-06), 화면은 그 본문에만 innerHTML을 쓴다. 닉네임·댓글·태그 등 나머지는 모두 textContent.
  - CSRF: 모든 JS 요청에 `X-XSRF-TOKEN` 헤더를 붙인다(SEC-10). 공통 `api.js` 한 곳에서 처리하면 빠뜨리지 않는다.
  - SNS 미리보기: 카톡·X는 JS를 실행하지 않으므로, 글 상세 주소만 서버가 og 태그(제목·요약·이미지)를 채워서 내려준다(BRD-07).

### 6. 블로그 개수 제한값: 설정 파일 + 환경변수 (D-68)

- **Decision**: `blog.limit.public=${BLOG_LIMIT_PUBLIC:3}`처럼 적어 환경변수로 덮어쓴다. 블로그를 만들 때는 개수를 세고 만드는 과정을 DB에서 잠근다(예: 회원 행 `SELECT ... FOR UPDATE`).
- **Rationale**: 이중화 때는 배포 환경 설정에서 값 하나만 바꾸면 모든 서버에 같은 값이 적용된다(바꾼 뒤 모든 서버 재시작). 동시에 두 번 누르면 두 요청이 모두 개수 확인을 통과할 수 있어 DB 잠금으로 막는다.

## 이중화 대비 (4.3)

### 서버 1대 → 2대 이상에서 바뀌는 점

| 항목 | 서버 1대 (1차) | 서버 2대 이상 | 필요한 작업 |
| --- | --- | --- | --- |
| 로그인 (SEC-04, JWT) | 로그인 정보는 토큰 안에, Refresh Token만 DB | 그대로. 모든 서버가 같은 DB를 봄 | 거의 없음 |
| 이미지 | 서버 디스크 | S3 | S3 구현 하나 추가 (SCL-02) |
| 7일 뒤 폐쇄 배치 (BLG-09) | 서버 1대에서 실행 | 한 서버에서만 실행 | 없음 (SCL-03) |
| IP별 요청 제한 | 서버 메모리 | Redis에서 함께 셈 | 저장소를 Redis로 교체 |
| 사용자 IP·HTTPS 확인 (SEC-10, 12) | 사용자에게서 직접 받음 | 로드밸런서를 거쳐 옴 | `X-Forwarded-For`, `X-Forwarded-Proto`를 읽도록 설정 |
| 인증 코드, 조회수, 로그인 실패 횟수, 알림 | DB | DB | 없음 (SCL-01) |

프록시 헤더 설정은 로드밸런서를 붙일 때 함께 켠다. 로드밸런서 없이 켜 두면 사용자가 헤더를 조작해 IP를 속일 수 있다.

이중화하면 새로 생기는 요구사항: 가용성(서버 한 대가 멈춰도 유지), 무중단 배포(옛 버전과 새 버전이 함께 도니 DB를 단계적으로 바꿈), 로그 모아보기(CloudWatch 등), 비용(서버 2대, 로드밸런서, Redis).

### 이중화 기술 후보

AWS를 쓰고 팀이 인프라를 직접 관리하지 않는 방향으로 추천을 붙였다. 서버를 늘릴 때 정한다.

| 영역 | 추천 | 다른 선택지 |
| --- | --- | --- |
| 1. 로드밸런서 | AWS ALB (상태 검사, HTTPS 처리) | Nginx 직접 설치 (무료, 단일 장애점) |
| 2. 서버 실행·자동 확장 | Elastic Beanstalk (jar만 올리면 됨) | ECS Fargate + Docker, EC2 + Auto Scaling |
| 3. 로그인 토큰 저장 | MySQL에 Refresh Token (채택, D-82) | Redis, 저장 안 함 |
| 4. 파일 저장소 | S3 (+ 나중에 CloudFront) | EFS |
| 5. 스케줄러 중복 방지 | ShedLock + DB | Quartz 클러스터 |
| 5. IP 요청 제한 | Bucket4j + Redis (ElastiCache) | AWS WAF |
| 6. DB | RDS for MySQL | Aurora MySQL, EC2에 직접 설치 |
| 7. DB 변경 관리 | Flyway (SQL 파일 버전 관리, 여러 서버가 동시에 떠도 한 번만 적용) | Liquibase, JPA `ddl-auto=update`(운영 금지) |
| 8. 배포 자동화 | GitHub Actions | Jenkins, AWS CodePipeline |
| 9. HTTPS 인증서 | AWS Certificate Manager | Let's Encrypt |
| 10. 로그·모니터링 | CloudWatch | Actuator + Prometheus + Grafana, ELK |
