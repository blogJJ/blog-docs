# Feature Specification: 메인블로그 플랫폼

**Feature Branch**: `001-main-blog`

**Created**: 2026-10-02 (요구사항분석서) · Spec Kit 형식 정리 2026-10-07 · 수정본(D-115까지) 반영 2026-10-07

**Status**: Draft (요구사항 확정, 구현 전)

**Input**: [요구사항분석서 1 · 기본 요구사항](../../docs/01-requirements/요구사항분석서_1_기본요구사항.pdf), [요구사항분석서 2 · 세부 정책과 결정 기록](../../docs/01-requirements/요구사항분석서_2_세부정책_결정기록.pdf), [요구사항분석서 3 · DB 설계(ERD)](../../docs/02-database/요구사항분석서_3_DB설계_ERD.pdf)

메인블로그는 회원가입, 로그인, 블로그 생성·참여를 담당하는 플랫폼이다. 실제 글쓰기 공간은 회원이 만든 개별 블로그다. 이 스펙은 메인블로그만 다룬다.

- **메인블로그**: 회원 계정, 블로그 생성과 참여, 소셜, 전체 관리
- **개별 블로그**: 회원이 만든 블로그. 만든 사람이 블로그장이 되고 다른 회원이 참여할 수 있다
- **관리 구조**: 메인 관리자는 블로그와 블로그장을, 블로그장은 자기 블로그의 멤버를 관리한다

요구사항 ID는 원본 문서의 `모듈-번호`를 그대로 쓴다: USR(회원), BLG(블로그), SOC(소셜), BRD(게시판), ADM(관리자), SEC(보안), SCL(확장성). 괄호 안 `D-번호`는 [research.md](research.md)의 결정 기록이다.

## 사용자 유형과 권한

블로그장과 블로그 멤버는 따로 가입하는 계정이 아니라 회원이 블로그별로 갖는 역할이다. 한 회원이 A 블로그에서는 블로그장, B 블로그에서는 멤버일 수 있다.

| 사용자 | 설명 |
| --- | --- |
| 비회원 | 로그인하지 않은 방문자 |
| 회원 | 메인블로그에 가입하고 로그인한 사용자 |
| 블로그 멤버 | 다른 사람의 블로그에 참여한 회원 |
| 부블로그장 | 블로그장이 지정한 멤버. 블로그장이 체크박스로 허용한 권한(정보 수정·멤버 관리·글 관리)만 가짐 (D-03, D-71) |
| 블로그장 | 블로그를 만든 회원. 그 블로그의 운영 권한을 가짐 |
| 메인 관리자 | 블로그와 블로그장을 관리하는 운영자. 회원은 검색·조회하고, 메인 프로필 신고가 오면 계정 경고·프로필 초기화·계정 정지만 한다(ADM-08). 블로그 활동(만들기·참여·글쓰기·댓글·좋아요·팔로우)은 하지 않음 (D-90) |

기능별 권한 (O = 가능, X = 불가, 본인 = 자기 것만)

| 기능 | 비회원 | 회원 | 블로그 멤버 | 블로그장 | 메인 관리자 |
| --- | --- | --- | --- | --- | --- |
| 블로그 목록·검색 | O | O | O | O | O |
| 공개 글 읽기 | O | O | O | O | O |
| 회원가입 | O | X | X | X | X |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 가입하고 로그인한다 (Priority: P1)

방문자가 이메일 인증을 거쳐 가입하고, 로그인 상태로 모든 개별 블로그를 오간다.

**Why this priority**: 계정이 없으면 블로그 생성·참여·글쓰기 어느 것도 할 수 없다. 모든 스토리의 바탕이다.

**Independent Test**: 새 이메일로 가입 → 로그아웃 → 로그인 → 다른 블로그 주소로 이동했을 때 로그인 상태가 유지되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 가입하지 않은 이메일, **When** 가입을 시작하면, **Then** 6자리 인증번호가 메일로 오고, 맞게 넣어야 비밀번호 입력 단계로 넘어간다.
2. **Given** 이미 가입된 이메일, **When** 가입을 시작하면, **Then** 화면에는 똑같이 "인증번호를 보냈습니다"가 보이고, 메일로는 "이미 가입된 이메일입니다" 안내가 간다.
3. **Given** 인증번호 단계, **When** 5번 틀리거나 10분이 지나면, **Then** 그 번호는 무효가 되고 다시 받아야 한다(재발송은 1분에 한 번).
4. **Given** 인증을 마친 방문자, **When** 비밀번호와 이름·닉네임·전화번호를 넣고 이용약관·개인정보 수집·이용에 동의하면, **Then** 가입이 끝난다.
5. **Given** 회원, **When** 로그인을 5번 연속 틀리면, **Then** 5분 동안 잠기고, 3번째 실패부터는 사람 확인(Turnstile)이 나온다.
6. **Given** "로그인 유지"를 체크하지 않은 회원, **When** 브라우저를 닫거나 30분 동안 직접 한 행동이 없으면, **Then** 로그아웃된다. 체크했으면 14일 유지된다.
7. **Given** 로그인한 회원, **When** 로그아웃하면, **Then** 서버의 Refresh Token이 폐기되고 쿠키가 지워진 뒤 메인으로 이동한다.

### User Story 2 - 블로그를 만들고, 찾고, 참여한다 (Priority: P1)

회원이 블로그를 만들어 블로그장이 되거나, 메인에서 블로그를 찾아 참여한다.

**Why this priority**: 이 플랫폼만의 핵심 모듈이다. 블로그가 있어야 글을 쓸 곳이 생긴다.

**Independent Test**: 회원 A가 승인제 블로그를 만들고, 회원 B가 검색으로 찾아 참여 신청 → A가 승인 → B의 "내 블로그 목록"에 나타나는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 회원, **When** 이름·주소·소개·대표 이미지·태그·공개 범위·참여 방식을 정해 만들면, **Then** 그 회원이 블로그장이 된다. 이미 쓰는 주소나 예약어 주소는 막힌다.
2. **Given** 공개(일부 공개 포함) 블로그를 3개 가진 회원, **When** 공개 블로그를 하나 더 만들려 하면, **Then** 막힌다. 동시에 여러 번 눌러도 제한을 넘지 않는다.
3. **Given** 일부 공개 블로그, **When** 공유 링크 없이 주소만으로 들어가면, **Then** 볼 수 없다. 링크로 들어온 비회원은 볼 수 있고, 회원에게는 "구독하기" 버튼이 보인다.
4. **Given** 블로그장이 공유 링크를 새로 만들면, **When** 이전 링크로 들어오면, **Then** 막힌다.
5. **Given** 자유 참여 블로그, **When** 참여를 누르면, **Then** 바로 멤버가 된다. 승인제면 블로그장 승인을 기다리고 결과가 알림으로 온다.
6. **Given** 참여 신청이 거절된 회원, **When** 7일 안에 다시 신청하면, **Then** 막힌다.
7. **Given** 메인 화면, **When** 블로그 목록을 보면, **Then** 공개 블로그만 최신순·인기순(멤버 수)으로 페이지를 나눠 보인다.
8. **Given** 메인 관리자 계정, **When** 블로그를 만들거나 참여하거나 댓글·좋아요·팔로우를 하려 하면, **Then** 막힌다. 글쓰기는 메인 공지만 된다.

### User Story 3 - 글을 쓰고 읽는다 (Priority: P1)

멤버가 참여한 블로그에 글을 쓰고, 누구나 공개 글을 읽고 댓글·좋아요를 남긴다.

**Why this priority**: 블로그의 본래 목적이다. 게시판은 공통 모듈로 메인(공지)과 모든 개별 블로그가 같이 쓴다.

**Independent Test**: 멤버가 이미지와 태그가 있는 글을 쓰고, 다른 회원이 댓글·대댓글·좋아요를 남기고, 비회원이 목록·상세를 읽는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 블로그 멤버, **When** 제목(1~30자)과 마크다운 본문으로 글을 쓰면, **Then** 서버가 HTML로 바꾸고 위험한 태그를 걸러 저장·표시한다.
2. **Given** 글 작성자가 아닌 블로그장·관리자, **When** 남의 글을 고치려 하면, **Then** 막힌다. 삭제는 할 수 있고 작성자에게 알림이 간다.
3. **Given** 글쓰기 화면, **When** jpg·jpeg·png·gif·webp가 아닌 파일이나 3MB를 넘는 파일, 11장째 이미지를 올리면, **Then** 막힌다. 확장자·MIME·파일 시그니처를 모두 확인하고 EXIF는 지운다.
4. **Given** 태그 입력, **When** `#Java 맛집 `처럼 넣으면, **Then** `java`, `맛집`처럼 앞의 #과 공백을 정리하고 영문은 소문자로 저장한다. 글 하나에 10개까지.
5. **Given** 댓글, **When** 대댓글에 다시 답하면, **Then** 1단계로 유지되고 답글 앞에 @닉네임이 붙는다.
6. **Given** 답글이 있는 댓글, **When** 지우면, **Then** "삭제된 댓글입니다"로 표시되고 답글은 남는다.
7. **Given** 같은 사람, **When** 같은 날 같은 글을 여러 번 열면, **Then** 조회수는 1번만 오른다.
8. **Given** 글 목록, **When** 한 페이지 개수를 고르면, **Then** 10·20·30개 중 선택한 개수로 번호 페이지가 나온다(기본 10개).

### User Story 4 - 블로그장이 멤버를 관리한다 (Priority: P2)

블로그장(멤버 관리 권한을 받은 부블로그장 포함)이 자기 블로그의 멤버를 경고·정지·강제 퇴장하고, 블로그 안 신고를 처리한다.

**Why this priority**: 메인 관리자가 모든 블로그를 살필 수 없어서, 블로그 단위 운영이 있어야 서비스가 굴러간다(D-43, D-44).

**Independent Test**: 블로그장이 멤버를 14일 정지 → 그 멤버가 그 블로그에만 못 들어가고 다른 블로그는 쓸 수 있는지 → 강제 퇴장 후 같은 전화번호로 재가입해도 참여 신청이 막히는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 블로그장, **When** 멤버를 정지(3일·14일·30일·영구)하면, **Then** 그 멤버는 로그인은 되지만 그 블로그에는 못 들어가고 기간과 사유를 안내받는다.
2. **Given** 그 블로그에서 정지를 3번 받은 멤버, **When** 블로그장 화면을 열면, **Then** 표시되고 블로그장이 직접 강제 퇴장을 처리한다.
3. **Given** 강제 퇴장된 회원, **When** 탈퇴 후 같은 이메일이나 전화번호로 재가입해 참여 신청하면, **Then** 블랙리스트(해시 비교)로 막힌다.
4. **Given** 전화번호 주인이 바뀌어 블랙리스트에 걸린 사람, **When** "문의하기"를 남기면, **Then** 블로그장 화면에 서버가 비교한 이름·전화번호 일치 여부가 보이고, 블로그장이 해제·거절한다.
5. **Given** 블로그장이 바뀐 블로그, **When** 새 블로그장이 블랙리스트를 보면, **Then** 열람만 되고 고치거나 지울 수 없다.
6. **Given** 멤버 관리 화면, **When** 블로그장이 멤버 정보를 보면, **Then** 이메일·전화번호는 가려서 보인다.

### User Story 5 - 블로그를 넘기거나 닫고, 탈퇴한다 (Priority: P2)

블로그장이 블로그를 다른 멤버에게 위임하거나 폐쇄하고, 회원이 블로그나 서비스를 떠난다.

**Why this priority**: 주인 없는 블로그가 생기지 않게 하는 규칙이라, 탈퇴 기능과 묶여 있다(D-15).

**Independent Test**: 10월 2일 오후 3시에 폐쇄 버튼 → 10월 9일 04:00 폐쇄 예정으로 저장, 즉시·10월 6일·10월 8일에 멤버와 구독자에게 알림이 가는지, 철회하면 멈추는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 블로그장, **When** 멤버에게 위임을 요청하면, **Then** 받은 멤버가 수락해야 넘어가고, 7일 안에 응답이 없으면 자동 취소되고 블로그장에게 알림이 간다.
2. **Given** 위임할 멤버가 없는 블로그, **When** 블로그장이 관리 화면을 열면, **Then** 위임 버튼 대신 폐쇄 버튼만 보인다.
3. **Given** 블로그장, **When** 폐쇄 버튼을 누르면, **Then** 누른 날짜 + 7일 04:00(Asia/Seoul)에 폐쇄되고, 블로그장을 뺀 멤버와 구독자에게 즉시·3일 전·1일 전 알림이 간다. 대기 중인 위임 요청은 자동 취소된다.
4. **Given** 폐쇄 예정 블로그, **When** 7일 안에 철회하면, **Then** 운영 중으로 돌아가고 같은 대상에게 철회 알림이 간다. 폐쇄 예정 중에도 글쓰기·댓글은 평소처럼 된다.
5. **Given** 폐쇄 예정 블로그, **When** 위임하려 하면, **Then** 먼저 폐쇄를 철회해야 위임 버튼이 보인다.
6. **Given** 운영 중이거나 폐쇄 예정인 블로그가 있는 블로그장, **When** 회원 탈퇴를 하려 하면, **Then** 막히고 블로그 목록과 위임·폐쇄 방법이 보인다.
7. **Given** 회원, **When** 비밀번호를 다시 확인하고 탈퇴하면, **Then** 로그인용 이메일이 즉시 비워져 같은 이메일로 바로 재가입할 수 있고, 쓴 글은 "탈퇴한 회원"으로 남는다.
8. **Given** 멤버, **When** 블로그를 떠나거나 강퇴되면, **Then** 그 블로그의 그 사람 글은 작성자가 "탈퇴한 계정"으로 바뀐다.

### User Story 6 - 계정을 찾고 정보를 고친다 (Priority: P2)

이메일이나 비밀번호를 잊은 회원이 스스로 계정을 되찾고, 회원 정보를 고친다.

**Why this priority**: 문의 없이 스스로 해결해야 운영 부담이 없다.

**Independent Test**: 이름+전화번호로 이메일 찾기 → 가려진 이메일 옆 [비밀번호 재설정] → 인증번호 입력 → 새 비밀번호로 로그인, 다른 기기는 로그아웃되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 비밀번호 찾기 화면, **When** 이메일을 넣으면, **Then** 가입 여부와 관계없이 같은 문구가 보이고, 가입된 이메일이면 6자리 번호(30분, 1회용, 5번 틀리면 무효)가 간다.
2. **Given** 맞는 인증번호, **When** 새 비밀번호를 두 번 넣으면, **Then** 바뀌고 다른 기기의 로그인이 모두 끊기며 로그인 잠금이 풀린다.
3. **Given** 이메일 찾기 화면, **When** 이름과 전화번호를 넣으면, **Then** 일치하는 계정의 이메일이 `ab***@gmail.com` 형식으로 가입일과 함께 보인다. 탈퇴 계정은 빠진다.
4. **Given** 같은 IP, **When** 10분에 6번째 이메일 찾기를 하면, **Then** 막힌다.
5. **Given** 회원, **When** 내 정보를 고치면, **Then** 닉네임·프로필 사진·전화번호·비밀번호(현재 비밀번호 확인)만 바뀌고, 이메일과 이름은 바꿀 수 없다.

---

### User Story 7 - 사람과 블로그를 따라가고, 찾는다 (Priority: P2)

회원이 다른 회원을 팔로우하고 블로그를 구독해 메인 피드에서 새 글을 보고, 통합 검색으로 블로그와 글을 찾는다.

**Why this priority**: 재방문 이유를 만든다. 핵심 흐름(US1~3)이 있어야 의미가 있다.

**Independent Test**: A가 B를 팔로우하고 C 블로그를 구독 → B와 C에 새 글 → A의 메인 피드 팔로우 탭·구독 탭에 각각 나오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 회원, **When** 메인 피드를 열면, **Then** 전체 최신·인기(좋아요 수) 공개 글과 함께 팔로우 탭, 구독 탭이 나뉘어 보인다.
2. **Given** 통합 검색, **When** 1글자나 공백·특수문자만 넣으면, **Then** 막힌다. 2~20자 검색어는 블로그(이름·소개), 글 제목, 태그, 작성자 닉네임에서 찾는다.
3. **Given** 검색 결과, **When** 정렬을 바꾸면, **Then** 관련도(기본)·최신·인기순으로 바뀌고, 비공개 블로그·숨김/삭제 글·내가 차단한 회원의 글은 나오지 않는다.
4. **Given** 회원, **When** 다른 회원을 차단하면, **Then** 그 회원의 글·댓글이 숨겨지고 서로의 팔로우가 풀린다. 단, 같은 블로그 멤버끼리는 그 블로그 안의 글이 보인다.
5. **Given** 블로그장이 차단한 회원, **When** 그 블로그에 참여 신청하면, **Then** 자동으로 거절된다.

### User Story 8 - 알림을 받는다 (Priority: P2)

회원이 종 아이콘을 눌러 탭별로 알림을 보고, 받을 알림 종류를 고른다.

**Why this priority**: 승인·위임·폐쇄처럼 응답이 필요한 흐름이 알림에 기대고 있다.

**Independent Test**: 댓글 알림을 끈 회원에게 댓글이 달려도 알림이 생기지 않고, 폐쇄 예정 알림은 끌 수 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 회원, **When** 종 아이콘을 누르면, **Then** 오른쪽 사이드바에 전체·댓글·좋아요·팔로우·구독·블로그·운영 탭이 보이고, 읽은 알림은 강조 색이 사라진다.
2. **Given** 내 정보 > 알림 설정, **When** 끌 수 있는 알림을 끄면, **Then** 새 알림은 만들지 않고 이미 받은 알림은 그대로 둔다.
3. **Given** 위임 요청·폐쇄 예정·내 글 삭제됨 같은 알림, **When** 설정 화면을 보면, **Then** 끌 수 없다([3.6 알림 표](#알림-종류)).
4. **Given** 화면이 열려 있는 회원, **When** 새 알림이 생기면, **Then** 30초 안에 보인다(폴링). 자동 확인 요청은 로그인 연장 활동으로 세지 않는다.

---

### User Story 9 - 신고하고, 메인 관리자가 처리한다 (Priority: P3)

회원이 문제를 신고하고, 신고 대상에 따라 블로그장이나 메인 관리자가 처리한다. 메인 관리자는 블로그와 블로그장을 관리한다.

**Why this priority**: 운영에 필요하지만, 초기 사용자가 적을 때는 블로그장 단위 관리(US4)로 대부분 해결된다.

**Independent Test**: 블로그장에 대한 신고 → 메인 관리자가 경고 3번 → 권한 박탈 → 가장 먼저 부블로그장이 된 사람에게 넘어가는지(없으면 7일 뒤 폐쇄 예정) 확인한다.

**Acceptance Scenarios**:

1. **Given** 회원, **When** 같은 대상을 2주 안에 다시 신고하면, **Then** 막힌다.
2. **Given** 블로그 안의 회원·글·댓글 신고, **When** 접수되면, **Then** 그 블로그의 블로그장에게 가고, 블로그 자체나 블로그장에 대한 신고는 메인 관리자에게 간다. 처리 결과는 신고자에게 알림으로 간다.
3. **Given** 경고 3번이 쌓인 블로그장, **When** 관리자가 조치하거나 바로 강퇴하면, **Then** 블로그장 권한이 박탈되고, 박탈된 사람은 일반 멤버로 남는다.
4. **Given** 부블로그장이 없는 블로그의 블로그장이 박탈되면, **When** 처리되면, **Then** "블로그장 권한 박탈로 인한 폐쇄 조치"로 7일 유예 후 폐쇄되고 BLG-09와 같은 알림이 간다.
5. **Given** 메인 관리자, **When** 회원 정보의 "전체 보기"를 누르면, **Then** 원문이 보이고 누른 기록이 남는다.
6. **Given** 메인 관리자, **When** 경고·강퇴·삭제·폐쇄·숨김을 하면, **Then** 누가 언제 무엇을 했는지 기록되고 1년 보관된다.
7. **Given** 메인 프로필 신고, **When** 메인 관리자가 계정을 14일 정지하면, **Then** 그 회원은 14일 동안 로그인과 읽기만 되고 모든 블로그에서 글·댓글·좋아요·팔로우를 못 한다.
8. **Given** 계정 정지된 회원이 블로그장인 블로그, **When** 정지 기간이면, **Then** 블로그 맨 위에 "블로그장 정지 중" 공지가 뜨고, 블로그장은 관리 기능을 못 쓰며, 그 기간에 들어온 블로그 안 신고는 메인 관리자에게 간다.

---

### Edge Cases

- 폐쇄 예정 7일 동안 블로그장은 탈퇴할 수 없다(D-18). 철회할 수 있는 동안은 블로그장이 남아 있어야 하기 때문이다.
- 대기 중인 위임 요청이 있는데 폐쇄 버튼을 누르면 위임 요청은 자동 취소된다.
- 서버가 꺼져 있던 날이 있으면, 다음 날 04:00 배치가 밀린 폐쇄와 알림을 처리한다. 같은 알림이 두 번 가지 않게 발송 기록을 남긴다.
- 서버가 여러 대면 04:00 배치는 ShedLock으로 한 서버에서만 돈다. 시간대(`Asia/Seoul`)를 빠뜨리면 AWS 기본 UTC로 한국 시간 오후 1시에 돈다.
- 공개 블로그를 비공개로 바꾸면 구독은 유지되지만 멤버가 아닌 구독자에게는 글이 안 보이고, 구독자에게 알림이 간다.
- 탈퇴한 회원의 이메일은 즉시 비우므로 같은 이메일로 바로 재가입할 수 있지만, 예전 글과는 연결되지 않는다.
- 폐쇄된 블로그의 주소는 30일 뒤 다른 사람이 쓸 수 있다.
- 비회원 조회는 IP+브라우저 해시로 "같은 사람"을 판단한다.
- 로그인 30분 연장은 사용자가 직접 한 행동(페이지 이동, 글·댓글 작성, 좋아요, 검색 등)으로 간 요청만 센다. 글쓰기 중에는 입력이 있으면 연장 요청을 보내고, 만료 5분 전에 "로그인을 연장할까요?" 창을 띄운다.
- 응답이 5초를 넘기면 기다리게 두지 않고 중단한 뒤 다시 시도하라고 안내한다.
- 전화번호는 1차에 중복을 허용한다. 문자 인증을 넣는 2차에 한 번호 한 계정으로 바꾼다.
- 인증번호 메일이 실패하면 그 번호는 바로 무효이고, 1분 재발송 제한에 걸리지 않아 바로 다시 받을 수 있다(OPS-07).

## Requirements *(mandatory)*

### Functional Requirements

#### 회원관리 (USR) — 회원 계정은 메인 한 곳에서 만들고 모든 개별 블로그가 공유한다

- **USR-01** (상) 가입: 이메일을 아이디로 쓴다. ① 이메일 인증 → ② 비밀번호 → ③ 이름·닉네임·전화번호 순서로 진행하고 모두 끝나야 가입된다. 이메일·닉네임은 중복 불가, 전화번호는 숫자만 저장하고 1차에는 중복 허용. ③단계에서 [필수] 이용약관, [필수] 개인정보 수집·이용 동의를 각각 받고 동의 시각을 저장한다. 만 14세 확인 체크는 두지 않는다. (SEC-01, SEC-02, D-08, D-24, D-91)
- **USR-02** (중) 이메일 인증: 6자리 번호를 Spring 서버가 만들어(SecureRandom) 해시로 저장하고 Gmail SMTP로 보낸다. 10분 만료, 5번 틀리면 무효, 재발송은 1분에 한 번이고 이전 번호는 무효. 이미 가입된 이메일도 화면 문구는 같고 메일로는 안내만 보낸다. 가입 마지막 단계에서 서버가 인증 완료 여부를 다시 확인한다. (D-10, D-28, D-42, D-69)
- **USR-03** (상) 로그인: 이메일·비밀번호. 로그인 상태는 모든 개별 블로그에서 유지된다. "로그인 유지" 체크박스가 있다. (SEC-03, SEC-04)
- **USR-04** (상) 로그아웃: 서버에서 Refresh Token을 폐기하고 토큰 쿠키를 지운 뒤 메인으로 이동한다. (SEC-04)
- **USR-05** (상) 회원 탈퇴: 비밀번호를 다시 확인한다. 블로그장인 블로그(폐쇄 예정 포함)가 있으면 모두 위임·폐쇄가 끝난 뒤에만 탈퇴할 수 있다. 탈퇴한 회원의 글은 "탈퇴한 회원"으로 남는다. (BLG-08, BLG-09, D-05, D-15, D-18)
- **USR-06** (중) 비밀번호 찾기·재설정: 6자리 번호(30분, 1회용, 5번 틀리면 무효) → 같은 화면에서 새 비밀번호 두 번 입력. 바뀌면 다른 기기 로그인 전부 로그아웃, 로그인 잠금 해제. 화면 문구는 가입 여부와 관계없이 같다. (SEC-05, D-25)
- **USR-07** (중) 회원 정보 수정: 닉네임·프로필 사진·전화번호·비밀번호(현재 비밀번호 확인). 이메일과 이름은 바꿀 수 없다. (SEC-02, D-21, D-32)
- **USR-08** (중) 이메일 찾기: 이름(앞뒤 공백 제거)+전화번호(숫자만) → 일치하는 계정의 이메일을 가려서 가입일과 함께 모두 표시, 탈퇴 계정 제외. 계정 옆 [비밀번호 재설정]은 회원 번호가 아니라 10분짜리 임시 토큰으로 요청한다. 같은 IP는 10분에 5번까지. (D-23, D-26, D-27)

#### 블로그 관리 (BLG)

- **BLG-01** (상) 블로그 생성: 이름, 주소, 소개, 대표 이미지, 태그(최대 10개, 규칙은 BRD-04와 같음, D-88), 공개 범위, 참여 방식. 만든 회원이 블로그장. 주소는 `/blog/{주소}` 경로 방식(D-70).
  - 공개: 목록·검색·피드에 보이고 누구나 본다.
  - 일부 공개: 목록·검색·피드에 안 나오고, 공유 링크(주소와 별개인 무작위 값)로 들어온 사람만 본다. 링크로 들어온 비회원도 볼 수 있다. 자동 구독은 없고 회원에게 "구독하기" 버튼이 보인다. 링크를 새로 만들면 이전 링크는 막힌다.
  - 비공개: 멤버만 본다. 공유 링크·공유 버튼이 없다. 공개→비공개로 바꾸면 구독은 유지되지만 멤버 아닌 구독자에게는 글이 안 보이고 알림이 간다. (D-37, D-49, D-50)
- **BLG-02** (상) 블로그 목록: 메인에 전체 공개 블로그를 최신순·인기순으로, 페이지를 나눠 보여준다. 인기순은 멤버 수가 많은 순서(D-89). 비공개·일부 공개는 제외.
- **BLG-03** (중) 블로그 검색: 이름, 소개, 태그(BLG-01에서 단 태그).
- **BLG-04** (상) 참여 신청: 자유 참여는 바로 멤버, 승인제는 블로그장 승인 대기. 대기 중인 신청이 있으면 다시 신청 불가, 거절되면 7일 뒤 재신청. 블로그장이 계정 정지 중이고 부블로그장이 없으면 정지 동안 참여 신청을 받지 않고 "블로그장 정지로 참여 신청이 일시 중지되었어요 (끝나는 날짜까지)"를 띄운다. (D-01, D-115)
- **BLG-05** (상) 참여 승인·거절: 결과는 신청자에게 알림. (SOC-04)
- **BLG-06** (상) 내 블로그 목록: 만든 블로그와 참여한 블로그를 나눠 보여주고 누르면 이동.
- **BLG-07** (중) 블로그 탈퇴: 멤버가 나간다. 블로그장은 위임 없이 나갈 수 없다. 떠난 멤버의 글은 작성자가 "탈퇴한 계정"으로 바뀐다. (D-33)
- **BLG-08** (중) 블로그장 위임: 받은 멤버가 수락해야 넘어간다. 거절·7일 무응답이면 유지되고 블로그장에게 알림. 위임할 멤버가 없으면 폐쇄 버튼만 보인다. 폐쇄 예정 중에는 위임 불가. 대기 중인 요청이 있을 때 폐쇄를 누르면 요청은 자동 취소. (D-16, D-20, D-31)
- **BLG-09** (중) 블로그 폐쇄: 누른 날짜 + 7일 04:00에 폐쇄. 블로그장을 뺀 멤버 전원과 구독자에게 즉시·3일 전·1일 전 알림. 7일 안에 철회 가능(같은 대상에게 철회 알림). 폐쇄 예정 중에도 평소처럼 운영. 폐쇄된 블로그의 글·사진·카테고리·블랙리스트는 30일 보관 후 삭제하고 주소는 비워 재사용 가능. 블로그 행은 1년 보관하는 제재·신고 기록이 가리키므로 남긴다. 같은 04:00 배치가 30일 지난 데이터와 만료된 Refresh Token도 지운다. (D-12, D-13, D-14, D-19, D-35, D-67, D-83, D-86)
- **BLG-10** (하) 생성 개수 제한: 공개(일부 공개 포함) 3개, 비공개 5개. 공개 개수는 설정값(`blog.limit.public=${BLOG_LIMIT_PUBLIC:3}`)으로 5개까지 늘릴 수 있다. 만들 때 개수 확인과 생성을 DB에서 잠가 동시 요청에도 제한을 넘지 않는다. (D-04, D-51, D-52, D-68)
- **BLG-11** (중) 멤버 강퇴와 블랙리스트: 강퇴된 멤버의 글은 "탈퇴한 계정"으로 바뀌고, 이름·이메일·전화번호가 해시로 그 블로그 블랙리스트에 오른다. 블랙리스트의 이메일·전화번호로는 그 블로그에 참여 신청할 수 없다(재가입해도). 기록은 블로그 안에 보관되고 블로그장이 바뀌어도 새 블로그장·부블로그장이 열람만 할 수 있다. 해제는 BLG-12로만. (D-34, D-55)
- **BLG-12** (하) 블랙리스트 해제 문의: 걸린 사람이 "문의하기"를 남기면 서버가 비교한 이름·전화번호 일치 여부가 보이고, 블로그장이 해제·거절한다. 결과는 알림.
- **BLG-13** (중) 멤버 경고·정지·강제 퇴장: 블로그장(멤버 관리 권한을 받은 부블로그장 포함)이 한다. 정지된 회원은 로그인은 되지만 그 블로그에만 못 들어가고 기간·사유를 안내받는다. 블로그 안의 회원·글·댓글 신고도 문제 없음·경고·정지·강제 퇴장 중 하나로 처리한다. 단, 블로그장 본인이나 블로그장이 쓴 글·댓글 신고와, 블로그장이 계정 정지 중일 때 들어온 신고는 메인 관리자가 처리한다(ADM-04, ADM-08). 블로그장이 계정 정지 중이고 부블로그장이 있으면 정지 동안 모든 부블로그장이 멤버 관리 권한을 임시로 갖고 그 기간의 신고도 처리한다(D-114). 그 블로그에서 정지 3번을 받은 멤버는 블로그장 화면에 표시되고 블로그장이 직접 강제 퇴장한다. (D-29, D-43, D-46, D-94, D-100, D-114)

#### 소셜 (SOC) — 회원 단위로 메인에서 한 번만 만들고 모든 개별 블로그가 같이 쓴다

- **SOC-01** (중) 팔로우·언팔로우, 블로그 구독. 팔로우한 회원의 새 글은 메인 피드 팔로우 탭, 구독한 블로그의 새 글은 구독 탭. 좋아요·팔로우·구독은 한 번만, 다시 누르면 취소. (D-02, BRD-09)
- **SOC-02** (하) 팔로워·팔로잉 목록.
- **SOC-03** (상) 프로필: 닉네임, 사진, 소개, 운영하는 블로그, 참여한 블로그, 팔로워 수.
- **SOC-04** (중) 알림: [알림 종류](#알림-종류) 표대로. 읽음 처리, 전체 삭제. 30초마다 확인(폴링). (D-39, D-56, D-72)
- **SOC-05** (하) 차단: 차단한 회원의 글·댓글을 숨기고 서로의 팔로우를 푼다. 같은 블로그 멤버끼리는 그 블로그 안의 글이 보인다. 블로그장이 차단한 회원의 참여 신청은 자동 거절. (D-36)
- **SOC-06** (중) 신고: 회원·블로그·글·댓글을 사유를 골라 신고. 같은 대상은 한 사람이 2주에 한 번. 블로그 안의 신고는 블로그장에게, 블로그·블로그장에 대한 신고(블로그장이 자기 블로그에 쓴 글·댓글 포함)와 메인 프로필에서 한 회원 신고는 메인 관리자에게. 신고 당시 대상 내용(글 제목·본문 앞부분, 댓글, 닉네임, 블로그 이름)을 함께 저장해, 원본이 30일 뒤 지워져도 1년 동안 확인할 수 있다. (ADM-04, BLG-13, D-45, D-85, D-94, D-95)

#### 게시판 (BRD) — BRD-01~07, 11은 공통 모듈, BRD-08~10은 메인 전용

- **BRD-01** (상) 글 작성·조회·수정·삭제: 제목 1~30자, 마크다운 본문 최대 5,000자(공백·마크다운 기호 포함, 서버에서 검사, D-92). 에디터는 Toast UI Editor. 수정은 작성자만. 삭제는 작성자, 블로그장(자기 블로그 글), 관리자. 블로그장·관리자가 삭제하면 작성자에게 알림. 삭제 전 확인 창. 임시저장은 1차에 브라우저에만. (SEC-06, SEC-07, D-07, D-58, D-74)
- **BRD-02** (상) 목록·페이징: 최신순, 번호 페이지, 한 페이지 10·20·30개(기본 10). (D-06, D-76)
- **BRD-03** (중) 카테고리: 블로그장이 관리, 카테고리별 보기.
- **BRD-04** (중) 태그: 글 하나에 10개, 1~20자, 한글·영문·숫자·`_`. 앞의 #과 앞뒤 공백 제거, 가운데 공백은 `_`, 영문은 소문자, 한 글 안 중복은 합침. 금칙어는 두지 않는다(D-98).
- **BRD-05** (중) 이미지 첨부: jpg·jpeg·png·gif·webp만(svg·동영상·문서·압축 제외). 글 이미지는 장당 3MB, 글 하나에 10장(한 번에 10MB). 프로필·블로그 대표 이미지는 3MB 1장. 확장자·MIME·파일 시그니처 모두 확인, UUID 이름으로 저장(원래 이름은 DB에만), EXIF 제거. 썸네일은 1차에 따로 만들지 않고 CSS로 줄여 표시(글 제목에 마우스를 올리면 사진 표시). (SEC-08, D-75)
- **BRD-06** (중) 댓글·좋아요: 댓글 1~500자, 대댓글 1단계 + 답글 앞에 @닉네임. 수정한 댓글에 "수정됨". 답글이 있는 댓글을 지우면 "삭제된 댓글입니다". (SOC-04, D-78)
- **BRD-07** (하) 공유: 1차는 링크 복사, 2차에 카카오톡(Kakao JS SDK)·X·페이스북·인스타·텔레그램. og 태그(og:title, og:description, og:image)를 서버가 채운다. 미리보기 이미지는 글의 첫 이미지, 없으면 블로그 대표 이미지를 줄여서. 주소 → 제목 → 이미지 순서. 공유 수는 집계하지 않는다. (D-59, D-66)
- **BRD-08** (중, 메인 전용) 통합 검색: 블로그(이름·소개), 글 제목, 태그, 작성자 닉네임. 분류바로 대상 선택. 블로그·글 제목은 MySQL FULLTEXT + ngram, 태그·닉네임은 일치 검색. 검색어 2~20자, 빈칸·공백·특수문자만이면 막음. 정렬은 관련도(기본)·최신·인기. 결과 제외: 비공개 블로그, 숨김·삭제 글, 내가 차단한 회원의 글. 결과가 없으면 "검색 결과가 없습니다". 최근 검색어는 본인만, 최대 10개, 개별·전체 삭제. 자동완성은 없음.
- **BRD-09** (상, 메인 전용) 메인 피드: 전체 블로그의 최신·인기 공개 글, 팔로우 탭, 구독 탭. 인기 글은 좋아요 수가 많은 순서. 볼 때마다 모아온다. (D-65, D-73, D-89)
- **BRD-10** (하, 메인 전용) 공지사항: 메인 관리자가 전체 회원에게.
- **BRD-11** (하) 조회수: 같은 사람이 같은 날 같은 글을 보면 1번만. DB 조회 기록 테이블로 센다. (D-77)

#### 메인 관리자 (ADM) — 모든 조치는 기록으로 남긴다

- **ADM-01** (상) 회원 관리: 전체 회원 검색·상세 보기. 회원 정지·강제 퇴장은 블로그장이 한다. 메인 관리자는 블로그장 강퇴, 블로그 폐쇄, 메인 프로필 신고에 따른 계정 제재(ADM-08)만 한다. (D-17, D-44, D-99)
- **ADM-02** (상) 블로그 관리: 전체 블로그 검색, 블로그장·멤버 수·글 수 보기, 숨김, 강제 폐쇄. 강제 폐쇄도 BLG-09처럼 누른 날짜 기준 7일 뒤 04:00에 폐쇄되고 같은 알림이 가며, 7일 안에 그 블로그의 블로그장이 철회할 수 있다. (D-96)
- **ADM-03** (중) 게시글·댓글 관리: 어느 블로그의 글이든 숨기거나 삭제.
- **ADM-04** (중) 신고 처리: 블로그·블로그장에 대한 신고(블로그장이 자기 블로그에 쓴 글·댓글 포함). 결과는 문제 없음, 블로그장 경고, 블로그장 강퇴, 블로그 폐쇄 중 하나. 메인 프로필에서 한 회원 신고와 블로그장이 계정 정지 중인 블로그의 신고도 처리한다(ADM-08). 신고자에게 알림. (SOC-06, D-38, D-94, D-95, D-99)
- **ADM-05** (하) 통계: 회원 수, 블로그 수, 일별 가입·글 수.
- **ADM-06** (중) 관리자 활동 기록: 누가 언제 무엇을 했는지. 개인정보 "전체 보기"도 기록. (SEC-09)
- **ADM-07** (중) 블로그장 경고·강퇴: 그 블로그에서 최근 1년 안에 경고 3번이거나 바로 강퇴하면 권한 박탈. 경고는 블로그별로 세고 1년 지난 경고는 뺀다(D-97). 부블로그장이 있으면 가장 먼저 부블로그장이 된 사람에게 넘기고, 없으면 7일 유예 후 폐쇄("블로그장 권한 박탈로 인한 폐쇄 조치" 공지, BLG-09와 같은 알림). 박탈된 사람은 일반 멤버로 남고 새 블로그장이 처분을 정한다. (D-30, D-54)
- **ADM-08** (중) 계정 경고·프로필 초기화·계정 정지: 메인 프로필 신고의 처리 결과는 문제 없음, 경고, 프로필 초기화(닉네임을 "회원"+회원 번호로, 사진·소개 삭제), 계정 정지(3·14·30일·영구) 중 하나. 정지된 회원은 로그인과 읽기만 되고 모든 블로그에서 글·댓글·좋아요·팔로우·구독·블로그 만들기·참여 신청을 못 한다. 기간이 끝나거나 관리자가 해제하면 풀린다. 정지된 회원이 블로그장이면 그 블로그마다 "블로그장 정지 중" 공지가 자동으로 뜨고, 정지 동안 블로그장은 블로그 관리 기능을 못 쓰며, 부블로그장이 있으면 정지 동안 모든 부블로그장이 멤버 관리 권한(참여 신청 승인, 멤버 제재, 블로그 안 신고 처리)을 임시로 갖고, 정지가 끝나면 원래 권한으로 돌아간다. 위임·폐쇄·부블로그장 지정과 권한 변경은 블로그장만 한다. 부블로그장이 없으면 그 기간에 들어온 블로그 안 신고는 메인 관리자가 BLG-13의 처리 결과로 대신 처리하고, 참여 신청은 이유를 띄워 일시 중지한다(BLG-04, D-115). 영구 정지면 블로그장 강퇴(ADM-07)와 같이 처리. (D-99, D-100, D-114, D-115)

### Non-Functional Requirements

#### 보안 (SEC)

- **SEC-01** 비밀번호는 bcrypt 해시로 저장한다. (D-81)
- **SEC-02** 비밀번호는 8~15자, 영문·숫자·특수문자 모두 포함, 대소문자 구분.
- **SEC-03** 로그인 5회 연속 실패 시 5분 잠금. 계정별 잠금 + IP별 요청 제한을 함께 둔다. (D-80)
- **SEC-04** JWT를 HttpOnly·Secure 쿠키에 담는다(localStorage 금지). 짧은 Access Token + Refresh Token(DB 저장). 로그아웃·비밀번호 변경 때 Refresh Token 폐기. "로그인 유지" 미체크: 세션 쿠키 + 30분 무활동 로그아웃, 체크: 14일. (D-53, D-61, D-62, D-82)
- **SEC-05** 비밀번호 재설정 인증번호: 1회용, 30분 만료, 5번 틀리면 무효.
- **SEC-06** XSS·SQL Injection 방지. 글 본문은 서버에서 마크다운 → HTML 변환 후 jsoup으로 걸러 보내고, 화면은 본문에만 innerHTML, 나머지 입력은 textContent. (D-64)
- **SEC-07** 모든 요청에서 서버가 블로그별 역할을 확인한다. A 블로그의 블로그장이 B 블로그를 관리할 수 없다.
- **SEC-08** 업로드 파일의 확장자·크기를 검사하고 실행 파일을 막는다.
- **SEC-09** 관리자 계정은 일반 회원과 분리하고 활동을 기록한다. 관리자 계정(role = ADMIN)은 블로그 만들기·참여·글쓰기·댓글·좋아요·팔로우를 할 수 없고, 메인 공지(BRD-10)와 관리 기능만 쓴다. (D-90)
- **SEC-10** 모든 통신은 HTTPS. 상태를 바꾸는 요청(POST·PUT·DELETE)은 CSRF 토큰 검사, JS 요청은 `X-XSRF-TOKEN` 헤더(공통 api.js에서 처리).
- **SEC-11** Spring Security로 인증·인가. 주소 단위로 비회원·회원·관리자를 나누고, 블로그별 역할은 `@PreAuthorize`로 확인. (D-09)
- **SEC-12** 보안 헤더: X-Frame-Options, X-Content-Type-Options: nosniff, Content-Security-Policy, Strict-Transport-Security, Referrer-Policy.
- **SEC-13** 로그인 3번 실패 후부터 Cloudflare Turnstile 사람 확인. (D-79)

#### 성능·사용성

- 메인·목록·검색은 1초 목표, 늦어도 2초. 5초를 넘기면 중단하고 다시 시도 안내. (D-48)
- PC·모바일 반응형. 지원 브라우저는 Chrome·Safari 최신 버전(OPS-06).
- 개별 블로그에서도 메인으로 돌아가는 상단 메뉴와 로그인 상태가 같게 보인다.

#### 확장성 (SCL) — 1차는 서버 1대, 이중화 대비 규칙은 지금부터

- **SCL-01** 서버 메모리에 상태를 두지 않는다(인증 코드, Refresh Token, 로그인 실패 횟수, 임시 데이터는 DB). IP별 요청 제한만 1차에 메모리, 이중화 때 Redis.
- **SCL-02** 파일 저장은 `FileStorage` 인터페이스로 분리, 1차는 디스크 구현만.
- **SCL-03** `@Scheduled` 작업에는 처음부터 ShedLock.

#### 운영 (OPS) — 백업, 오류, 로그, 배포 확인, 개발 규칙

- **OPS-01** DB 백업: 매일 03:00 전체 백업, 7일치 보관. 백업 파일은 서버 밖 저장소에 복사하고(위치는 배포 환경을 정할 때) 운영자만 연다. 복구 절차를 문서로 두고 공개 전에 한 번 복구해 본다. (D-101)
- **OPS-02** 오류 처리: 화면과 응답에 스택 트레이스·SQL·클래스 이름·서버 경로를 보이지 않는다. API 오류는 HTTP 상태 + 같은 형식의 JSON(`code`, `message`), 화면 주소는 404·403·500 안내 화면(메인으로 가기). 500에는 로그에서 찾을 오류 번호를 보여 준다. (D-102)
- **OPS-03** 로그: 서버 파일에 날짜별로, 30일 보관. 서버 오류, 로그인 실패(가린 이메일, IP), 권한 거부(403), 요청 제한 초과(429)를 남긴다. 비밀번호·JWT·Refresh Token·인증번호·쿠키·CSRF 토큰은 남기지 않고, 이메일·전화번호는 4.4 방식으로 가린다. 관리자 활동은 DB 기록(ADM-06). (D-103)
- **OPS-04** 상태 확인: `/actuator/health`만 연다. 결과는 UP/DOWN만(DB 연결 포함), 세부 정보와 다른 Actuator 주소는 닫는다. 이중화 때 로드밸런서가 쓴다. (D-104)
- **OPS-05** 자동 빌드·테스트: GitHub Actions가 PR과 main 푸시마다 `./gradlew build`(코드 모양 검사, 테스트)를 돌리고, 통과해야 merge한다. (D-105)
- **OPS-06** 지원 브라우저: Chrome·Safari 최신 버전. PC는 Windows·Mac Chrome과 Mac Safari, 모바일은 Android Chrome과 iPhone Safari에서 확인한다. 다른 브라우저는 따로 확인하지 않는다. (D-106)
- **OPS-07** 메일 발송 실패: 화면에 "메일을 보내지 못했어요. 잠시 뒤 다시 시도해 주세요"(가입 여부와 상관없이 같은 문구). 서버가 자동으로 다시 보내지 않고, 보내지 못한 인증번호는 바로 무효이며 1분 재발송 제한에 세지 않는다. 실패는 오류 로그에 남긴다. Gmail 하루 한도(일반 계정 약 500통)에 가까워지면 메일 발송 서비스로 바꾼다. (D-107)
- **OPS-08** DB 변경: Flyway `V번호__설명.sql`로만 바꾼다. main에 merge된 파일은 고치거나 지우지 않고 다음 번호 파일을 추가한다. `ddl-auto=validate`라 엔티티와 DB가 다르면 서버가 뜨지 않는다. 테이블·컬럼을 바꿀 때는 `erd_tables.sql`을 먼저 고친다. (D-108)
- **OPS-09** 테스트: SC-002~SC-007, SC-009, SC-011은 자동 테스트로 확인한다. DB를 쓰는 테스트는 Testcontainers로 띄운 실제 MySQL 8에서 Flyway 파일로 만든 스키마로 돌린다(H2 등 대체 DB를 쓰지 않음). PR마다 CI에서 돌고, 테스트를 끄거나 건너뛰어 통과시키지 않는다. SC-001·SC-008·SC-010은 사람이 확인한다. (D-109)
- **OPS-10** 라이브러리 보안: Dependabot이 매주 Gradle 라이브러리와 GitHub Actions 업데이트 PR을 연다. 보안 취약점 알림과 보안 업데이트 PR도 켠다. 업데이트 PR도 CI를 통과해야 하고 자동으로 merge하지 않는다. 큰 버전 업데이트는 팀이 따로 정한다. (D-110)
- **OPS-11** 실행 환경: local·prod 프로필(테스트는 test). 기본 설정은 운영 기준으로 안전하게 두고 local에서만 푼다. 비밀값(JWT 비밀키, DB 비밀번호, Gmail 앱 비밀번호, Turnstile 비밀키)은 환경변수로만 받는다. prod는 비밀값이 비었거나 예시 값이면 뜨지 않고, 쿠키에 Secure를 붙이며 http를 https로 돌려보낸다. (D-111)
- **OPS-12** API 문서: springdoc-openapi로 코드에서 만든다. local에서만 `/swagger-ui.html`, `/v3/api-docs`를 열고 prod에서는 404. (D-112)

#### 개인정보 가려서 보여주기 (4.4)

| 보는 사람 | 보이는 항목 | 표시 방식 |
| --- | --- | --- |
| 본인 (내 정보) | 이메일, 이름, 닉네임, 전화번호 | 모두 그대로 |
| 블로그장 (멤버 관리 화면) | 이메일, 이름, 닉네임, 전화번호 | 이메일·전화번호는 가림 |
| 부블로그장 (멤버 관리 권한이 있을 때) | 블로그장과 같음 | 권한이 없으면 멤버 정보를 볼 수 없음 |
| 다른 회원 (프로필) | 닉네임, 프로필 사진, 소개 | 이메일·이름·전화번호는 보이지 않음 |
| 메인 관리자 | 이메일, 이름, 닉네임, 전화번호 | 기본은 가림. "전체 보기"를 누르면 보이고 기록이 남음 |
| 이메일 찾기 결과 | 이메일 | 가림 |

- 이메일: @ 앞 처음 2글자만 보이고 나머지는 `***`. @ 앞이 2글자 이하면 첫 글자만. `abcdef@gmail.com → ab***@gmail.com`
- 전화번호: 가운데 4자리를 가림. `010-1234-5678 → 010-****-5678`
- 가리는 처리는 서버가 응답을 만들 때 한다. (D-22)

#### 데이터 보관·삭제 (4.5)

삭제·탈퇴·폐쇄된 데이터는 30일 보관 후 완전히 지운다(그동안 화면에 안 보임). 완전 삭제는 매일 04:00 배치가 폐쇄 처리와 함께 하고, 만료된 Refresh Token도 같은 배치에서 지운다. (D-40, D-83)

| 대상 | 30일 동안 | 30일 뒤 |
| --- | --- | --- |
| 탈퇴한 회원의 개인정보 | 로그인 불가, 안 보임. 로그인용 이메일은 즉시 비움 | 개인정보 삭제, 글은 "탈퇴한 회원"으로 남음 |
| 삭제한 글·댓글·사진 | 안 보임. 관리자가 복구 가능 | 완전 삭제 |
| 폐쇄된 블로그 (글·사진·카테고리) | 안 보임 | 글·사진·카테고리·블랙리스트 완전 삭제, 주소는 비워 다른 사람이 쓸 수 있음. 블로그 행은 남김 (D-86) |
| 알림 | 알림함에 보임 | 삭제. 내 정보에서 7일로 줄이거나 직접 일괄 삭제 가능 |

예외: 인증번호·임시 토큰은 만료되거나 쓰면 바로 삭제. 블로그 블랙리스트는 그 블로그가 있는 동안 해시로 보관. 관리자 활동·신고·경고·정지 기록은 1년. (D-60) 서버 로그는 30일(OPS-03), DB 백업은 7일(OPS-01)이라 30일 뒤 지운 데이터도 백업에는 최대 7일 더 남는다.

- **블로그 (blogs)**: 주소, 이름, 공개 범위(PUBLIC/LINK_ONLY/PRIVATE), 참여 방식(OPEN/APPROVAL), 상태(ACTIVE/CLOSING/CLOSED).
- **블로그 멤버 (blog_members)**: 회원과 블로그의 연결. 역할(OWNER/MANAGER/MEMBER), 정지 상태, 정지 횟수.
- **참여 신청, 위임 요청, 구독, 블랙리스트, 문의**: 블로그 관리 흐름의 기록.
- **게시글, 댓글, 태그, 이미지, 좋아요, 조회 기록**: 게시판 공통 모듈.
- **팔로우, 차단, 알림, 알림 설정, 최근 검색어**: 소셜.
- **신고, 멤버 제재, 블로그장 제재, 계정 제재, 관리자 활동 기록**: 운영 기록(1년 보관).
- **인증번호, 임시 토큰, Refresh Token, 배치 잠금**: 인증·인프라.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 메인 화면, 블로그 목록, 검색 결과가 1초 안에 응답한다(늦어도 2초). 5초를 넘는 요청은 사용자에게 다시 시도 안내가 나간다.
- **SC-002**: 블로그 A의 블로그장 계정으로 블로그 B의 관리 기능(멤버 제재, 글 삭제, 정보 수정, 폐쇄)을 호출하면 모두 거부된다.
- **SC-003**: 가입·비밀번호 찾기 화면의 응답만 보고 어떤 이메일이 가입되어 있는지 알아낼 수 없다.
- **SC-004**: API 응답 어디에도 권한 없는 사람에게 가리지 않은 이메일·전화번호가 담기지 않는다.
- **SC-005**: 폐쇄 버튼을 누른 블로그는 예정 시각 다음 04:00 배치 안에 폐쇄되고, 멤버와 구독자는 폐쇄 알림 3번(즉시, 3일 전, 1일 전)을 각각 정확히 한 번씩 받는다.
- **SC-006**: 공개 블로그 생성 버튼을 동시에 여러 번 눌러도 회원당 공개 블로그 수가 제한(기본 3개)을 넘지 않는다.
- **SC-007**: 같은 사람이 같은 날 같은 글을 여러 번 열어도 조회수는 1만 오른다.
- **SC-008**: 서버를 2대로 늘릴 때 코드 변경 없이 설정(이미지 저장소, IP 요청 제한 저장소, 프록시 헤더)만 바꾸면 된다.
- **SC-009**: 없는 주소, 잘못된 입력, 서버 오류를 일부러 낸 요청의 응답과 화면 어디에도 스택 트레이스·SQL이 보이지 않고, 로그 파일에는 비밀번호·토큰·인증번호가 한 번도 나오지 않는다.
- **SC-010**: 전날 백업 파일 하나로 빈 DB를 복구하면 서버가 다시 떠서 `/actuator/health`가 UP을 돌려준다.
- **SC-011**: prod 프로필로 띄운 서버에서 `/swagger-ui.html`과 `/v3/api-docs`는 404를 돌려주고 로그인 쿠키에는 Secure가 붙어 있으며, JWT 비밀키를 빼고 prod로 띄우면 서버가 뜨지 않는다.

## Assumptions

- 1차는 서버 1대로 운영한다. 이중화 기술(ALB, Elastic Beanstalk, S3, Redis 등 10개 영역)은 서버를 늘릴 때 정한다([research.md](research.md#이중화-기술-후보)).
- 문자(SMS) 인증은 2차로 미룬다. 그래서 1차는 전화번호 중복을 허용하고 이메일 찾기는 이름+전화번호로 한다.
- 메일 발송은 Gmail SMTP로 시작하고, 사용자가 늘면 메일 발송 서비스로 바꾼다.
- 개별 블로그 내부 기능(꾸미기·테마·메뉴, 멤버 목록 화면 등)은 다음 스펙에서 다룬다. 이 스펙의 계정·역할·게시판 모듈을 그대로 쓴다.
- 메인 공지사항은 `main` 블로그의 글로 저장한다(DB 설계).
